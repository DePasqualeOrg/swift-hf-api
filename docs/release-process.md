# Release process

`swift-hf-api` ships as two linked releases:

- the **Rust binary artifact** release, tagged `hfapi-rust-<version>`, published by the `rust-release.yml` workflow as a SE-0482 `staticLibrary` artifactbundle (Apple and Linux slices in one zip);
- the **Swift package** release, tagged `<version>`, whose `Package.swift` points at the binary asset URL and checksum for that artifact.

The package release must come after the Rust artifact release, because `Package.swift` needs a published binary to pin. The two tag series share the same `<version>` string by convention, but they can move independently: a Swift-only patch release reuses whichever Rust artifact is currently pinned in `rust/Pin.json`.

This document covers both halves: the architecture that binds them, the release workflow, the maintainer commands, the drift guards, and how to build locally before a release exists.

## How the pieces fit together

- **`rust-release.yml`**: publishes a new artifactbundle as a GitHub release. The release carries **three downloadable assets** — the zip, its SwiftPM-style checksum, and a machine-readable manifest — plus auto-generated release notes as the release body. The workflow is `workflow_dispatch`-only.
- **`rust/Pin.json`**: a verbatim copy of the release manifest for the currently pinned version. `Package.swift` mirrors its `artifactbundle_url` and `checksum` values as inline `let` constants (inside the `// pin:start`/`// pin:end` markers) because manifest-evaluation file I/O is unreliable for URL-based dependency consumers.
- **The drift guards** keep `Pin.json`, `Package.swift`, and the committed FFI wrapper in sync with the Rust source. They run in `ci.yml` on every PR and again inside `rust-release.yml` at publish time (see [Drift guards](#drift-guards)).
- **`scripts/rust/release/cut-release.sh`**: the single maintainer command that dispatches the Rust release and bumps the pin.
- **`scripts/rust/release/publish-package-release.sh`**: tags and publishes the Swift package release.

`rust/Pin.json` is absent until the first Rust artifactbundle release is cut. While it is absent, `ci.yml` skips the pin guards (they have nothing to compare against) and the package resolves only via the local-artifactbundle override (see [Building against a local artifactbundle](#building-against-a-local-artifactbundle)).

## UniFFI bindgen and the committed Swift wrapper

The Rust↔Swift FFI is generated by [UniFFI](https://mozilla.github.io/uniffi-rs/). The helper `scripts/rust/build/build-uniffi-bindings.sh` invokes a workspace-pinned `uniffi-bindgen-swift` binary against the freshly built host static library and emits three artifacts into `rust/target/uniffi-bindings/`:

- `HFAPIRust.h` – C header that the artifactbundle exposes.
- `module.modulemap` – modulemap that names the C module `HFAPIRust`. The per-platform build scripts post-process this with `scripts/rust/build/strip-modulemap-uses.sh` to drop the bindgen-emitted `use "Darwin"`/`use "_Builtin_*"` directives, since those reference clang modules that exist only on Apple and break the module load on Linux.
- `HFAPIFFI.swift` – the high-level Swift wrapper.

The per-platform build scripts (`build-rust-apple-slices.sh` for Apple, `build-rust-linux-archives.sh` for Linux) shell out to the helper as part of producing their slices, then copy the use-stripped header and modulemap into their staging dir's `include/`. The artifactbundle assembler picks whichever staging dir's `include/` is present (preferring Apple when both are; the contents are identical post-strip) and stages it once at the bundle's top level. Every variant in `info.json` references that single `include/` via `staticLibraryMetadata.headerPaths`/`moduleMapPath`, since the C ABI is platform-neutral.

The Swift wrapper is **committed** at `Sources/HFAPIFFI/Generated/HFAPIFFI.swift` and consumed by the `HFAPIFFI` SwiftPM target (a non-product target that the public `HFAPI` target depends on). The committed wrapper is the source of truth for what the binary release exposes. To keep the two in sync:

- **None of the build scripts write to `Sources/HFAPIFFI/Generated/`.** `build-uniffi-bindings.sh` writes to `rust/target/uniffi-bindings/`; the per-platform build scripts additionally write to their staging dirs. CI and the release workflow only ever read the committed wrapper.
- **`scripts/rust/regenerate-wrapper.sh`** is the developer-facing command that rebuilds the bindgen artifacts and copies the freshly generated wrapper over the committed one (prepending `// swift-format-ignore-file` so the generated file is exempt from the project's swift-format lint). Run it after touching `rust/src/`, `rust/uniffi.toml`, or the bindgen binary version, then commit the result.
- **`scripts/rust/check-wrapper-drift.sh`** fails if the committed wrapper drifts from what the bindgen would emit. It runs a bindgen-only build (host static library plus the bindgen binary; no per-target matrix or bundle assembly), so it is fast enough to gate every PR. When an `apple-build/` or `linux-build/` staging directory is present, it also diffs the staged `include/HFAPIRust.h` and `include/module.modulemap` (post-strip), so a release run guarantees the headers shipped in the bundle match the source at `GITHUB_SHA`.

UniFFI 0.31.x's Swift bindgen is pinned to a fork via `[patch.crates-io]` in `rust/Cargo.toml` for two Swift-side fixes: the fork preserves leading U+FEFF BOM bytes when lifting strings (using Swift's native UTF-8 decoder rather than Foundation's `NSString` decoder), and it exposes `uniffi.toml` flags that hide the lower-level `HFAPIRust` import and FFI converter helpers from public Swift interfaces. **TODO:** drop that block and bump the `uniffi` version in `[dependencies]` once the needed Swift bindgen fixes ship in a uniffi-rs release. Several other patches to `hf-hub` and `xet-core` are pinned the same way; `docs/upstream-patches.md` tracks each fork branch and the PR-shaped commit ready to file upstream.

## The Rust release workflow (`rust-release.yml`)

The workflow is split into four jobs to keep the cross-platform builds independent and the write boundary tight:

- **`apple-build`** (macos-latest, `contents: read`): verifies the dispatched commit matches `expected_commit` via `.github/actions/verify-expected-commit`, runs `build-rust-apple-slices.sh` to cross-compile the five Apple targets and stage them under `rust/target/apple-build/` (with macOS and iOS Simulator lipoed into universal slices), runs the wrapper-drift check, and uploads the staging dir as the `apple-build` workflow artifact.
- **`linux-build`** (ubuntu-22.04, `contents: read`): verifies the dispatched commit, installs the aarch64 cross-toolchain plus a Cargo linker mapping for `aarch64-unknown-linux-gnu` (so the x86_64 host can produce both Linux slices), runs `build-rust-linux-archives.sh`, and uploads `rust/target/linux-build/` as the `linux-build` workflow artifact.
- **`assemble`** (macos-latest, `contents: read`): downloads both build artifacts, runs `assemble-artifactbundle.sh` to produce `HFAPIRust-<version>.artifactbundle.zip` plus a SwiftPM-style checksum, asserts that all five variants ended up in `info.json` (a partial bundle would resolve silently on the host triple but break consumers building for unsupported triples), runs `swift build` against the staged bundle as a smoke test (via `HFAPI_RUST_LOCAL_ARTIFACTBUNDLE_PATH`, since the URL is still unpublished), computes the source hash, writes the release manifest (`hash_schema_version: 3`), generates release notes with `scripts/rust/release/rust-release-notes.py`, and uploads the four files (zip, checksum, manifest, release notes) as one workflow artifact.
- **`publish`** (macos-latest, `contents: write`, environment `rust-release`): downloads the assembled artifacts and creates the GitHub release with `gh release create --target "$GITHUB_SHA"`, attaching the zip, checksum, and manifest as assets and using the generated notes as the release body. It refuses to overwrite an existing `hfapi-rust-<version>` tag, and marks pre-release versions (those with a `-` suffix) with `--prerelease`.

The split puts the approval prompt exactly at the write boundary. A failed build, a mismatched `expected_commit`, a missing variant, or a smoke-test failure stops the workflow before the publish job is ever queued for approval. The `verify-expected-commit` step lives in `.github/actions/verify-expected-commit/action.yml` so the apple-build and linux-build jobs share one source.

## One-time setup: the `rust-release` Environment

The `publish` job references `environment: rust-release`. Create a repository Environment named `rust-release` under **Settings → Environments → New environment**:

1. Add the maintainer as a required reviewer.
2. Confirm "Prevent self-review" is **disabled** (the maintainer is their own reviewer).
3. Save.

Without this configuration the publish job fails when it tries to enter the environment.

## Cutting a Rust release

Run `scripts/rust/release/cut-release.sh <version>` from the branch you want to publish — typically a Rust-touching PR branch. The script:

1. Validates that the target `hfapi-rust-<version>` release does not already exist, the working tree is clean, and the branch is not detached. It refuses to run from `main`/`master` unless `HFAPI_ALLOW_RELEASE_FROM_MAIN=1`.
2. Records local `HEAD` as the expected commit and verifies the branch is pushed (local `HEAD` equals `origin/<branch>`), so the workflow runs against exactly that commit.
3. Dispatches `rust-release.yml` against the current branch with `version` and `expected_commit`.
4. Waits for the run to finish (skip with `--no-wait`).
5. Verifies the completed run's `headSha` equals the expected commit and that the published release exists.
6. Downloads the release manifest asset (`HFAPIRust-<version>.manifest.json`).
7. Cross-checks that the manifest's `version`, `git_commit`, and `source_hash_sha256` match what the script expects (recomputing the local source hash).
8. Writes the manifest verbatim to `rust/Pin.json`, rewrites `Package.swift`'s inline `hfapiRustArtifactBundleURL`/`hfapiRustArtifactBundleChecksum` constants from the manifest's `artifactbundle_url`/`checksum` (editing only inside the `// pin:start`/`// pin:end` block), and commits both files with the message `Pin Rust artifactbundle to hfapi-rust-<version>`.

Push the branch afterward to trigger CI with the refreshed pin, then open or update the PR.

## Publishing the Swift package

After the pin-bump commit is on `main`, tag and publish the package release:

```bash
bash scripts/rust/release/publish-package-release.sh <version> [<ref>] [--yes]
```

That script:

- reads the Rust artifact version pinned at the ref and verifies the corresponding `hfapi-rust-*` release exists upstream (Swift and Rust versions are independent, so the pinned Rust version may lag the package version);
- verifies `Package.swift`'s inline pin matches `rust/Pin.json` at the ref (via `check-package-swift-pin.sh`);
- creates and pushes the annotated tag `<version>` (with a confirmation prompt; pass `--yes` to skip), cleaning up the tag locally and on `origin` if a later step fails;
- creates the matching GitHub release with auto-generated "What's Changed" notes between the previous package tag and the new one, prefixed with a link to the matching Rust artifact release. Pre-release versions get GitHub's `--prerelease` flag.

Swift-only patch releases reuse the existing Rust pin — pass the new package version and the script tags whatever commit you point it at without requiring a fresh Rust artifact release.

## Example: cutting `0.4.0` end to end

```bash
# On a release-prep PR branch (clean tree, pushed to origin):
bash scripts/rust/release/cut-release.sh 0.4.0
git push origin <branch>
# ...review and merge the pin-bump PR into main...

# Then on main:
git checkout main && git pull
bash scripts/rust/release/publish-package-release.sh 0.4.0
```

## Drift guards

Each guard exists as a script and runs both in `ci.yml` (on every PR) and, where relevant, inside `rust-release.yml` at publish time. The pin guards live in the `pin-guards` CI job and **no-op while `rust/Pin.json` is absent**; the wrapper-drift guard runs in its own `wrapper-drift` CI job and in the release workflow's `apple-build` job.

### Source-hash guard (`check-pin.sh`)

Recomputes the canonical source hash via `scripts/rust/hash-source.sh` and compares it against `rust/Pin.json.source_hash_sha256`, also asserting that `hash_schema_version` matches the value this repo's tooling supports (currently `3`). On mismatch it fails with a message telling the maintainer to cut a new Rust release on the branch.

The hash covers more than `rust/src` — its input allowlist is `rust/Cargo.lock`, `rust/Cargo.toml`, `rust/src`, `rust/uniffi.toml`, `rust-toolchain.toml`, `Sources/HFAPIFFI/Generated`, `scripts/rust/build`, `scripts/rust/regenerate-wrapper.sh`, and `.github/workflows/rust-release.yml`. So changing a dependency rev, the toolchain, the committed wrapper, or a build script all drift the pin and require a fresh release. This makes it structurally impossible to ship a release where the Rust source and the pinned artifactbundle disagree.

### Package.swift pin guard (`check-package-swift-pin.sh`)

Asserts that `Package.swift`'s inline `hfapiRustArtifactBundleURL` + `hfapiRustArtifactBundleChecksum` constants match `rust/Pin.json`'s `artifactbundle_url` + `checksum` fields. Runs in CI against the working tree, and again in `publish-package-release.sh` against the tagged ref (via process-substituted `git show` paths) before the package tag is pushed.

### Pre-release pin guard (`check-prerelease-pin.sh`)

Fails when `rust/Pin.json.version` contains a `-` suffix (e.g. `0.4.0-rc.1`). It runs in CI only on PRs targeting `main`, keeping pre-release pins off the default branch. To merge a pre-release pin intentionally — for example, to validate the release flow on a release-prep branch — set the environment variable `ALLOW_PRERELEASE_PIN=1`. (Note: the guard reads this from the process environment, so a repository variable must be wired into the `pin-guards` job via `env:` for the override to take effect in CI.)

### Wrapper-drift guard (`check-wrapper-drift.sh`)

Rebuilds the host static library, regenerates the Swift wrapper into a temp dir, and `git diff --no-index`'s the result against the committed `Sources/HFAPIFFI/Generated/HFAPIFFI.swift` (and, when staging dirs are present, the staged header/modulemap). A nonzero diff fails with a message pointing at `regenerate-wrapper.sh`. Runs in CI's `wrapper-drift` job and in the release workflow's `apple-build` job, so a drifted wrapper fails before any artifact is published.

## Trust boundary

`rust-release.yml` has `contents: write` (on the `publish` job) and runs the workflow file from whatever ref is dispatched. A branch that modifies the workflow could publish bogus assets if a maintainer dispatches the release against it.

- Do not dispatch `rust-release.yml` against an external contributor's PR branch directly. Merge or cherry-pick the reviewed Rust source changes onto a maintainer-owned branch (or `main`) first, then run `cut-release.sh` there.
- Treat the release workflow and `cut-release.sh` as maintainer-only tools. External contributors cannot trigger `workflow_dispatch` — only repository write access can — but this discipline protects against social-engineering dispatches.

## Building against a local artifactbundle

Before the first release exists (or for development and pre-release validation), `Package.swift` accepts the environment variable `HFAPI_RUST_LOCAL_ARTIFACTBUNDLE_PATH` to point at an unzipped local artifactbundle directory (its name must end in `.artifactbundle`; a `.zip` path will not work):

```bash
HFAPI_RUST_LOCAL_ARTIFACTBUNDLE_PATH=rust/target/artifactbundle/HFAPIRust.artifactbundle \
    swift build
```

CI builds this bundle on the fly via the `.github/actions/build-host-artifactbundle` composite action, which also exports the variable for subsequent steps. The release workflow's `assemble` job uses the same mechanism to smoke-test the freshly built bundle before publishing, and `verify-docs.sh` requires the override on a checkout where `Package.swift`'s pin slot is still empty (the pre-first-release state).

## Bumping the hash schema

The `hash_schema_version` field exists so the hash input set can evolve without silently accepting stale pins. To bump it:

1. Change `scripts/rust/hash-source.sh` (or whichever input set is changing).
2. Bump `SUPPORTED_HASH_SCHEMA_VERSION` in `scripts/rust/release/check-pin.sh`, the `hash_schema_version` value the `assemble` job writes into the manifest, and any other tooling that asserts it.
3. Merge the schema change.
4. Cut a new Rust release under the new schema. Until that release is cut, the drift guard fails because the existing pin's schema version is stale.
